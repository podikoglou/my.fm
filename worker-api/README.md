# my.fm Worker API

The Cloudflare Workers port of the my.fm API. The existing Bun API in `api/`
stays unchanged and independent; see `MIGRATION.md` for the migration plan.

This package contains the `worker-foundation`, `worker-auth`, `worker-read-api`,
and `worker-ingestion` slices: an Alchemy stack, a D1 database, the complete
application schema, Better Auth with Spotify OAuth, the user and recent-scrobble
read endpoints, a one-minute Spotify ingestion job, and a health endpoint.

## Commands

```sh
bun run dev        # alchemy dev: Worker in workerd with a local D1 simulator
bun run deploy     # alchemy deploy: create/update Cloudflare resources
bun run destroy    # alchemy destroy: remove this stage's resources
bun run typecheck  # tsgo
bun run lint       # oxlint
bun run fmt        # oxfmt
bun run fmt:check  # oxfmt --check
bun run test       # bun test
bun run db:generate # drizzle-kit generate: write SQL into ./drizzle
```

## Layout

```text
alchemy.run.ts        Alchemy stack, Worker resource, bindings, cron, and WorkerEnv type
src/worker.ts         Worker entrypoint; forwards requests to Hono and runs the cron
src/app.ts            Hono application, CORS, route mounts, and health endpoint
src/auth.ts           Better Auth configuration and Spotify provider
src/auth-middleware.ts Session guard and application user on the request context
src/types.ts          Hono application environment (bindings and variables)
src/data/validators.ts Onboarding username and name schemas
src/database.ts       D1 database resource and migration wiring
src/db/index.ts       Per-request Drizzle client for the D1 binding
src/db/schema.ts      Drizzle tables and relations
src/db/queries/       Database queries for reads, ingestion inserts, and the cursor
src/ingestion/        Spotify client, play storage, and the Cron Trigger run
src/routes/           User and scrobble routes
drizzle/              SQL migrations generated by drizzle-kit
test/                 Bun tests and the shared in-memory D1 harness
```

The Worker uses Alchemy's async Worker form: plain `fetch` and `scheduled`
handlers with a typed `env`. Effect is installed because Alchemy requires it as
a peer; Effect services are introduced at service boundaries in later slices.

## Authentication

`/api/auth/*` is served by Better Auth 1.7.20 through the Drizzle relations-v2
adapter over D1. The configuration mirrors the Bun API: Spotify OAuth, the
`avatarUrl` image field, generated usernames, and nanoid IDs.

A Worker has no `process.env`, so Alchemy binds the same values the Bun API
reads from the environment:

- `BETTER_AUTH_SECRET`
- `BETTER_AUTH_URL`
- `FRONTEND_URL`
- `SPOTIFY_CLIENT_ID`
- `SPOTIFY_CLIENT_SECRET`
- `SPOTIFY_REDIRECT_URI`

CORS allows `FRONTEND_URL` with credentials, matching the Bun API.

The Bun API also pushed new users into an in-memory fetch queue from a
`user.create.after` hook. That queue is process-local state and has no meaning
in a Worker; the account scan in the ingestion section replaces it.

## Read API

Every `/user/*` and `/scrobble/*` route runs the session middleware first and
returns `401` without a Better Auth session. The routes and responses mirror
the Bun API:

- `GET /user/me` returns the current user's application fields.
- `GET /user/byUsername?username=...` and `GET /user/byId?id=...` return the
  public fields, or `404` when the user does not exist.
- `PUT /user/onboard` accepts a form with `username` and `name`, and updates
  the current user once.
- `GET /scrobble/getRecent?username=...&offset=...&limit=...` returns recent
  scrobbles with their track, album, and ordered artists.

The read routes do not fetch, create, or update Spotify data. Ingestion is a
separate Cron Trigger; `PUT /user/onboard` remains because it is part of the
current `/user/*` interface.

Drizzle 1.0 uses the relations-v2 filter form (`where: { userId }`,
`orderBy: { scrobbleDate: "desc" }`) instead of `eq`/`desc` inside relational
queries. The generated SQL and the response data are the same.

## Ingestion

A Cloudflare Cron Trigger runs the ingestion Worker every minute:

```ts
crons: ["* * * * *"];
```

Each run reads every account with `providerId = "spotify"`, then processes
each account:

1. Get a valid Spotify access token from Better Auth.
2. Read the user's `lastRecentTracksFetchTime` cursor.
3. Fetch 50 recently played tracks on the first run, or 6 tracks after the
   cursor on later runs.
4. Store the play, track, album, artists, and scrobble rows.
5. Move the cursor to the newest play. If a later fetch returns no plays, move
   the cursor to the current time.

If a user has more than one Spotify account row, the scan uses the first row
and skips the rest, matching the Bun API's account selection.

The in-memory Bun queue and the `user.create.after` hook are not ported. The
account scan finds new users, and `lastRecentTracksFetchTime` is both the fetch
cursor and the only scheduling state.

Better Auth 1.7.20 selects provider tokens by the local account row ID, so the
scan also reads `accounts.id` and calls `getAccessToken` with
`{ accountId, userId }`. The Bun API passed `providerId` to Better Auth 1.6.5.
The account and its refresh behaviour are the same.

Scrobble IDs are deterministic: the first 16 bytes of SHA-256 over
`${userId}:${scrobbleDate.toISOString()}`, written as 32 lowercase hex
characters. A re-fetched play gets the same ID, so `onConflictDoNothing` keeps
the write idempotent. The Bun API used `Bun.hash.wyhash`, which Workers do not
have. The new D1 database starts empty, so these IDs do not need to match the
Bun API's.

Plays are written in batches of up to ten. D1 counts one `db.batch()` call as
one query against the invocation limit. A single batch for a whole fetch would
be one query, but a failure would roll back every play; ten plays per batch
bounds the rollback, and an initial fetch of fifty plays is still only five
batches. Every insert in a batch uses `onConflictDoNothing`.

A failure for one account is logged with `console.error` and does not stop the
other accounts. The failed user's cursor is not advanced, so the next run
retries it.

### Known limitations

The Bun scheduler fetched one user every five seconds with a regular limit of
six. A one-minute Cron Trigger cannot reproduce that cadence. If a user plays
more than six tracks in a minute, the cursor can move past plays that were not
fetched. This is accepted for the port; scheduling changes are separate work.

The scan runs in one invocation. D1 allows 1,000 queries per invocation on
Workers Paid and 50 on Free, and each account costs about four queries in the
steady state (account lookup, cursor read, one batch, cursor write) plus one
Spotify subrequest. Roughly ten accounts fit in a Free invocation; roughly two
hundred fit in a Paid invocation. An initial fetch costs more because it uses
five batches. The account query has no ordering or rotation, so accounts beyond
the budget can be skipped on every run. The scheduling rewrite must add
rotation or split the scan across invocations.

## Client types

`src/app.ts` exports `AppType`, the Hono RPC type for the API. A client can use
it with `hc<AppType>` from `hono/client`, as the web application does with the
Bun API's `AppType` today.

The package exposes the type as `@my.fm/worker-api`. The app depends on the
workspace package and enables `allowImportingTsExtensions`, because the Worker
sources use `.ts` import specifiers. Switching the app's import from
`@my.fm/api` to `@my.fm/worker-api` is a type-only change; the route types are
compatible.

## Database and migrations

Drizzle is the only schema author. Alchemy applies pending migrations from
`drizzle/` to D1 on deploy; the Worker never runs migrations at request time.

```text
edit src/db/schema.ts
  -> bun run db:generate
  -> review and commit drizzle/
  -> bun run deploy applies the new migrations
```

Drizzle 1.0 writes each migration to
`drizzle/<timestamp>_<name>/migration.sql` with a sibling `snapshot.json`.
Alchemy applies the directories in order and records them in its own
`__alchemy_migrations` table.

The first deploy creates an empty database. There is no data migration from
`api/data.db`.

## Secrets

Do not commit secret values. `.env` is ignored; `.env.example` lists the
required names and local placeholders. Use an Alchemy profile for deploy
credentials, and the bindings above for application secrets.

## Verification

```sh
bun run dev

curl http://localhost:1337/health
# {"status":"ok","database":"ok"}

curl http://localhost:1337/api/auth/get-session
# null

curl -X POST http://localhost:1337/api/auth/sign-in/social \
  -H 'content-type: application/json' \
  -d '{"provider":"spotify"}'
# {"url":"https://accounts.spotify.com/authorize?...","redirect":true}

curl -i http://localhost:1337/user/me
# 401 {"error":""}

curl http://localhost:1337/cdn-cgi/handler/scheduled
# ok
```

`GET /health` runs `SELECT 1` against the bound D1 database. The Spotify URL
confirms the provider, client ID, scopes, and callback wiring; completing a
real sign-in needs Spotify credentials and a registered redirect URI. The
`/user/*` and `/scrobble/*` routes require a session cookie from that sign-in.

`/cdn-cgi/handler/scheduled` is the local workerd endpoint for the Cron
Trigger. With no Spotify accounts it runs the scan and stores nothing; it
confirms that the scheduled handler and the Spotify SDK module load in the
Worker.

The Bun tests run the same migrations against an in-memory SQLite database
through the D1 driver, so the auth routes, relational read queries, ingestion,
and route guards are exercised without a network or a deployed Worker. The read
tests seed a user, track, album, artists, and scrobbles, then assert the public
user shape, newest-first scrobble order, pagination, and the `401` guard. The
ingestion tests seed a Spotify account, fake the Spotify client, and assert the
initial and regular limits, cursor updates, batched writes, deterministic IDs,
and per-account error isolation. A real Spotify sign-in is still needed to
verify the live API call.
